# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

React 19 + TypeScript frontend for AceReStreamer (re-streams AceStream links as HLS or MPEG-TS). Built with Vite, uses bun as package manager, Chakra UI v3 for components, TanStack Router (file-based) and TanStack Query for data. The FastAPI backend lives at `../acere` (sibling directory, not covered by this file).

This is an admin/config UI, not a viewing app — end users are expected to watch in an IPTV app or VLC. The only playback here is the admin stream preview (see Components below).

## Commands

- `bun run dev` — start the Vite dev server
- `bun run typecheck` — `tsc --noEmit`
- `bun run lint` — Biome check with `--write --unsafe` (auto-fixes)
- `bun run build` — `tsc -p tsconfig.build.json` + `vite build` into `dist/` (used by `docker/Dockerfile.combined`'s build stage, which copies the output into the backend image). Note both build scripts typecheck against `tsconfig.build.json`, not the `--noEmit` config that `bun run typecheck` uses.
- `bun run build-aio` — same, but `vite build --emptyOutDir --outDir ../acere/dist` (the "all-in-one" mode where FastAPI serves the built frontend directly). This is the only production deployment — a separately hosted frontend is dev-only via `bun run dev`.
- `bun run generate-client` — regenerates `src/client/` from `./openapi.json` via `@hey-api/openapi-ts` (see `openapi-ts.config.ts`). Don't run this directly to get fresh types — use `../scripts/generate-client.sh` from the repo root inside the backend's venv, which first dumps the live OpenAPI schema from the FastAPI app into `openapi.json` and then runs this.
- `bun run generate-frontend-paths` — walks `routeTree.gen.ts` and `public/` to emit a JSON list of every frontend route/asset path, used by the backend to know which paths to hand off to the SPA in all-in-one mode.

There is no test runner configured in this package (no vitest/jest). Correctness is enforced via `typecheck` + `lint` plus manual verification in the browser.

## Architecture

**Routing**: `src/routes/` is TanStack Router file-based routing. `__root.tsx` sets up the root route (404 handling, lazy-loaded router/query devtools outside production). `_layout.tsx` is the shared app shell (sidebar + header + `PageTitleContext` for per-page titles via `usePageTitle()`), and every page under `src/routes/_layout/*.tsx` renders inside it via `<Outlet />`. `routeTree.gen.ts` is auto-generated by the `tanstackRouter` Vite plugin — never edit it by hand.

**API client**: `src/client/` is entirely auto-generated from the backend's OpenAPI schema (see Commands above) — never hand-edit it. Services are grouped by backend router and exposed as `<Name>Service` classes (`AcePoolService`, `ConfigService`, `FrontendService`, `HealthService`, `MediaIptvService`, `ScraperService`, `StreamsService`, `XtreamCodesService`). `main.tsx` points the generated client at the backend with `OpenAPI.BASE = baseURL()`. `src/helpers.ts` exports `baseUrl()` (both named and as the default export, so import sites name it either way) — it resolves the API origin from the `VITE_API_URL` env var if set, stripping trailing slashes, otherwise falls back to `window.location.origin`. That fallback is what makes all-in-one mode (frontend served by the same FastAPI process) work without any env config.

Note that the streaming endpoints (`/hls/…`, `/ts/…`) and the playlist endpoints (`/iptv…`) are **not** called through the generated client — code that needs them builds the URL from `baseURL()` directly (e.g. `useVideoPlayer.ts`, `IptvInfo.tsx`).

**Components**: organized by feature area under `src/components/`:
- `Admin/` — config, health, scraper, stream/channel and remote-config management screens, each with a `*Management.tsx` entry component plus a subdirectory of supporting pieces (e.g. `Admin/Streams/Table.tsx`)
- `Index/` — the status/dashboard page (`AcePoolSection.tsx`, instance table, backend info, quality cells)
- `info/iptv/` — IPTV/Xtream Codes connection info shown to end users: XC credentials plus the HLS and MPEG-TS playlist URLs
- `Common/` — app chrome (Header, Sidebar, NotFound)
- `ui/` — thin wrappers around Chakra UI v3 primitives (button, dialog, table, code, etc.) — prefer these over importing straight from `@chakra-ui/react` when a wrapper already exists here, since they carry project-specific defaults (e.g. `ui/code.tsx` sets the monospace font).

**Stream preview player**: `Admin/Streams/PreviewPlayer.tsx` is the one place video actually plays. It uses shaka-player against the backend's `/hls/{content_id}` endpoint, loaded via a dynamic `import("@/hooks/useVideoPlayer")` so shaka stays out of the initial bundle — keep it that way when touching this. Supporting hooks: `usePreviewStream` (which stream is selected), `useStreamStatus` (playback/health text shown in the status table).

**State/data fetching**: TanStack Query for all server state (`useQuery`/`useMutation`, no store library). The two bits of cross-component UI state that need to outlive route navigation — `usePreviewStream` and `useStreamStatus` — use a module-level variable plus a `Set` of listeners, exposed through a hook (`useSyncExternalStore` in the former, `useEffect`+`useState` in the latter). Deliberate, not an oversight; don't reach for a store library to "fix" them. Toasts via `useCustomToast`, form/API error formatting via `handleError` in `src/utils.ts`.

**Path alias**: `@/*` maps to `src/*` (configured in both `tsconfig.json` and `vite.config.ts`).

**Chakra UI skills**: `.agents/skills/chakra-ui-builder`, `chakra-ui-refactor`, `chakra-ui-migrate` contain reference material for building/refactoring/migrating Chakra v3 components — check there for theming and component-choice guidance before introducing new UI patterns.
